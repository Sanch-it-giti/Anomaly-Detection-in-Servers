# M6B design — synthetic registered real-backend integration only

7 November 2026. Source review: M6B readiness, M6A design/completion, M5B-1 contracts and M5B-2 completion. M5B-2 equals ARIMA at h=1 and is worse at h=12; this integration neither erases that result nor claims improvement. No real observation or historical outcome ledger feeds this milestone.

## Frozen reference and compatibility

The only detector input remains fixed persistence/rule_v2 absolute error, independent h=1/h=12, age-three genuine persistence availability. ARIMA/XGBoost/adaptive errors and policy fallback errors are not reference samples. The M6A implementation and configuration are pinned, unchanged: first32 genuine errors median/max(1.4826 MAD,0.1), clipped z±4, delta0.05, warning4/alarm8, minimum64 genuine errors in288 elapsed ticks, capacity288, 24-tick cooldown and frozen normalization. Fourth missing tick clears current-era detector state once per gap; old-era outcomes stay audit-only. See the original design for exact PH equations/support-loss rearming. There is no new CPU-level channel or drift response.

BackendForecastV1 identifies its envelope policy version as m5b1_real_backend_v1, whereas M6A strictly accepts ForecastRecordV2 persistence/rule_v2. A new immutable bridge retains the complete original forecast/outcome and creates an explicitly declared compatibility view. Only baseline persistence source rule_v2 is admitted; identities, exact target, horizon, sequence, era, value and genuine outcome must agree. The view maps only the envelope policy version, preserving actual source version, original forecast/outcome IDs and causal context. Its origin_tick_id is an explicit backend-sequence locator, not a claim to reproduce the original tick's string ID; the original sequence and backend tick ledger supply authoritative linkage. No historical or backend contract is weakened or modified.

## Driver lifecycle and chronology

Composition uses the unchanged AdaptiveRealStreamingV1 factory and exact registered RealAdapter objects. Inputs are only generated five-minute genuine/missing events; arbitrary adapter injection is unavailable. The backend reveals, resolves exact targets, applies telemetry/support/selector state, updates both models, issues shadows and unchanged adaptive/persistence forecasts. Then the wrapper advances detector clocks and observes eligible already-matured persistence errors. Every new monitor receipt has its own monotone sequence, the completed backend barrier sequence, M6B configuration hash and original M6A detector configuration hash. Backend records retain their legacy not_implemented detector field; the external monitor is a distinct versioned ledger.

This is a deliberate recording-order integration difference from M6A's monitor-before-issuance demonstration, requested for M6B. It changes neither error availability nor detector statistics: each detector consumes exactly the same current-target errors at the same five-minute timestamp. Monitoring has no mutation/callback route into source forecasting or selection. Enabled/disabled runs must have identical full backend steps, including state hashes, decisions, selection and outcomes. Existing selector rules remain active unchanged; any loss-driven switches are distinct backend events, never drift-driven actions.

## Checkpoints, boundaries and verification gate

The existing registered fixture recipe builds96 synthetic observations only: ARIMA uses known (1,1,1) coefficients with actual state-space filtering, not parameter optimization; two direct XGBoost boosters are trained solely on throwaway generated data before replay. No historical checkpoint is loaded for prediction or refitted. The historical registry is opaque hash verification only. The fitting guard prohibits all replay fitting. Synthetic checkpoint hashes must remain unchanged after runs.

Predeclared integration fixtures: sustained slope increase (280 ticks; .1 to .5 at160), existing gaps/forecast-failures fixture (450), existing ARIMA update-failure fixture (180). These reuse established deterministic backend fault contexts. They are mechanics tests, not real-data detection experiments or independent evidence. All settings/fixtures are fixed before saved execution. The run is capped2304 ticks and4GiB process RSS; recent detector state is bounded, audit ledgers are small in-memory harness artifacts. Per-case times exclude checkpoint build; aggregate includes build/audits. Process high-water RSS is cumulative, not isolated model allocation.

The new source gate pins config/module/runner/tests/this design after passing the complete suite and before saved execution. Exclusive versioned roots reject existing IDs before checkpoint generation. Original690 artifacts (571 historical plus M6A inventory and inventory itself) are protected by SHA-256; historical six selected checkpoint bundles also checked through the original registry. All original execution locks remain untouched; new config disallows real-data execution, confirmation, replay refitting, selector changes, drift response and intervals.

Saved audits independently reconstruct the unchanged detector from original linked persistence forecasts/outcomes and verify exact target arithmetic, chronological barriers, enabled/disabled parity, source links, saved hashes and detector receipts. Tests cover delayed h12, missingness/reset/cooldown/support, repeated alarms, numerical/update failures, suffix invariance, immutable records, registry rejection and preservation. No M7 intervals, real-data evaluation, LSTM or dashboard follows automatically.
